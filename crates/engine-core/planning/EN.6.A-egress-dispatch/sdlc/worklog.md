## Task 2 — PASSED (1 attempt)
What: WorkflowTriggerDispatch now POSTs {workflow_type, data} to /events/ carrying an X-API-Key header, enforces an 8-hop chain-depth cap, prefers an injected in-process Dispatcher (fire-and-forget) over the loopback HTTP fallback, and channel_transport_live() routes WorkflowTrigger sends through it and every other channel to UnwiredChannelTransport.
Decisions: Extended HttpPost with an additive `post_with_headers` trait method (default delegates to `post`, ignoring headers) rather than changing `post`'s signature — keeps every existing call site (persist_to_brain.rs, proposal_generator/persist_to_brain.rs) and their tests untouched, while making StubHttpPost::last_headers() assertable for the X-API-Key requirement. This touches http_post.rs, which isn't in task 2's stated file list, but was necessary to satisfy the task's own explicit X-API-Key acceptance criterion (asserted via StubHttpPost) — flagging as a deliberate, minimal, backward-compatible deviation.; api_key is read from env var ENGINE_EVENTS_API_KEY at WorkflowTriggerDispatch::new() (empty default) and overridable via with_api_key(); channel_transport_live(events_url) takes only the URL per the task's stated signature — task 5 (serve wiring, out of scope here) is expected to call with_api_key to match engine-serve's configured AppState::api_key.; chain_depth cap and parent_run_id/envelope_id propagation: the event Value is forwarded as-is (any ids the caller already stamped travel through untouched — this seam never fabricates one), with only `chain_depth` read (default 0) and incremented; requests at or above MAX_CHAIN_DEPTH=8 return Err before any network/dispatch call.; In-process Dispatcher preference is fire-and-forget via tokio::task::spawn_blocking running a fresh current-thread runtime, not a direct `.await` on `workflow.run()` — Workflow::run's OnProgress has no Send bound, so its future is !Send and cannot be held across an await point inside the Send-bound `#[async_trait]` ChannelTransport::send (or handed to plain tokio::spawn). This also mirrors /events/'s own EN.5.F non-blocking contract: the receipt reflects the handoff, not the child run's outcome.; dispatch_with_event's Err (unknown workflow_type or policy failure) is treated as 'not registered here' and falls through to the HTTP path rather than immediately failing, so an injected Dispatcher with only some workflow_types registered still routes out-of-process targets correctly.
Validated: gating checks (fast tripwire)
