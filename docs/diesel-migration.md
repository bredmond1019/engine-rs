# Porting `engine-store` to `diesel-async`

**Decision:** [brain D84 Amendment 3](file:///Users/brandon/Dev/agentic-portfolio/docs/decisions/D84-engine-rs-owns-the-engine-tables.md)
settled the ORM fork in favour of `diesel-async`. **Amendment 4 (2026-09-12) keeps `sqlx` in the
workspace beside it** — the operator ruled against removing it, since spike 2 measured both stacks
coexisting in one binary — so this is a staged port of the queries, not a swap. The port is
registered as `EN.ticket.engine-store-queries-move-to-diesel-async`.
This doc is the playbook so none of it is re-derived. It is written to be *worked through*, in
order.

Everything below was measured in three spikes (2026-09-03 and 2026-09-07) — links at the bottom.
Where a claim has a number attached, that number came from a run, not an estimate.

## The two rules that are not optional

If you remember nothing else from this page, remember these. Both cover a failure that is
**silent** — it compiles, it runs, it returns wrong data or fails only in production.

> ### 1. Every read uses `#[derive(Selectable)]` and `.select(T::as_select())`
>
> A plain positional `Queryable` load transposes same-typed columns with **no error and no
> warning**. Measured: a struct with `step`/`kind` swapped returned `step="decision" kind="plan"`.
> `journal` has four adjacent `Text` columns (`campaign_id`, `step`, `kind`, `reason`), so this is
> live risk here specifically. With `as_select()` the same deliberate swap returned correct data —
> the select clause and the struct move together.

> ### 2. `schema.rs` is generated by `diesel print-schema`. Never hand-write a `table!`
>
> Diesel type-checks Rust against `table!`; **it never sees the database**. A hand-written `table!`
> declaring `created_at -> Timestamptz` against the real `TIMESTAMP` column compiled *and ran
> clean* — which is exactly the trap
> [`0001_create_journal.sql`](../crates/engine-store/migrations/0001_create_journal.sql)'s own
> comment already warns about. `print-schema` read the live DB and emitted `Timestamp` correctly.
> Regenerating `schema.rs` belongs in the migration loop, next to running the migration.

## Quickstart — the toolchain

```bash
cargo install diesel_cli --no-default-features --features postgres

# generate schema.rs for THIS engine's tables only — never the whole database (see Trap 4)
export DATABASE_URL="postgres://<user>@localhost:5432/<engine-db>"
diesel print-schema events journal node_invocations > crates/engine-store/src/schema.rs
```

Crate dependencies (versions as spiked — `diesel 2.2.12`, `diesel-async 0.5.2`):

```toml
diesel = { version = "2", features = ["postgres", "uuid", "serde_json", "chrono"] }
diesel-async = { version = "0.5", features = ["postgres", "deadpool"] }
# REQUIRED — see Trap 1. Not optional, and the error it prevents is confusing.
futures-util = { version = "0.3", features = ["async-await"] }
```

## The traps, in the order they will bite you

| # | Trap | What you see | Fix |
|---|---|---|---|
| 1 | `futures-util` resolves without its `async-await` feature | `error[E0433]: cannot find try_join in futures_util` — inside `diesel-async`'s own source, so it reads like a broken crate | Add the explicit `futures-util` dependency above |
| 2 | `AsyncConnectionWrapper::establish` is ambiguous | `error[E0599]: no method named expect found for Pin<Box<dyn Future…>>` | Fully qualify: `<AsyncConnectionWrapper<AsyncPgConnection> as diesel::Connection>::establish(url)` |
| 3 | `postgres:///dbname` URL form is rejected | `pool: Error occurred while creating a new object: invalid configuration` — **at runtime, per request**, not at boot | Use an explicit host: `postgres://user@host:5432/db`. **Audit all three hardcoded strings before deploying** — see "Before this reaches the Mini" |
| 4 | `print-schema` with no table list pulls in the Brain's tables | 18 tables emitted, synthesised `Vector`/`Tsvector` types, `varchar[]` warnings | Always pass the explicit table list. Resolves itself once D84's database split lands |
| 5 | Migrations are sync-only | `diesel_migrations::MigrationHarness` does not accept an async connection | Wrap with `AsyncConnectionWrapper` inside `tokio::task::spawn_blocking` — see below |

### Running migrations from async code

`diesel_migrations` is sync-only. `diesel-async` ships the bridge; it must run off the async
executor:

```rust
fn run_migrations(db_url: &str) {
    let mut wrapper: AsyncConnectionWrapper<AsyncPgConnection> =
        <AsyncConnectionWrapper<AsyncPgConnection> as diesel::Connection>::establish(db_url)
            .expect("establish sync wrapper");
    wrapper.run_pending_migrations(MIGRATIONS).expect("run migrations");
}

tokio::task::spawn_blocking(move || run_migrations(&url)).await?;
```

This is the intended one-shot startup use. It was **not** tested under load — treat it as a boot
path, not a request path.

## What the port actually touches

Smaller than it looks. All query logic is in one file.

| Location | What changes |
|---|---|
| `crates/engine-store/src/postgres.rs` (411 lines, 10 query functions at `036c317`; the spikes measured 305 lines and 8, before `EN.14.F` added the two `node_invocations` functions) | The whole port. The only place query logic lives |
| `crates/engine-store/src/schema.rs` | New — generated, not written |
| `crates/engine-serve/src/durable.rs`, `journal.rs`, `orphan.rs` | **Type alias only.** They thread `PgPool` as an opaque handle and delegate every query to `engine_store::*`. No query logic to port |
| `crates/engine-store/migrations/` | Nothing required — `sqlx` stays (D84 Amendment 4), so `sqlx::migrate!` can keep applying these unless the port finds a concrete reason to move them |

### The four query shapes, and how each translates

All four were verified working against the real table shapes.

| Shape | Site | Diesel form |
|---|---|---|
| Insert | `insert_journal_row` | `#[derive(Insertable)]` + `insert_into(..).values(..)` |
| Select + filter + order | `list_journal_rows_for_campaign` | `.filter(..).order(..).select(T::as_select()).load()` |
| Upsert, `created_at` excluded | `postgres.rs:105` | `.on_conflict(id).do_update().set((col.eq(excluded(col)), ..))` — verified `created_at` preserved while `updated_at` moved |
| Nested JSON path | `postgres.rs:164` | **No typed form.** See below |

**The one query that stays unchecked.**
`WHERE task_context->'metadata'->'completion' IS NULL` has no native typed form for a `json`
(not `jsonb`) column. It works only through the escape hatch:

```rust
.filter(diesel::dsl::sql::<diesel::sql_types::Bool>(
    "task_context->'metadata'->'completion' IS NULL",
))
```

That is a raw, unchecked string — today's safety level, so not a regression, but **9 of the 10 query
functions gain compile-time checking and this one filter does not** (the spikes counted 7 of 8,
before `node_invocations` existed). Migrating `task_context` to `jsonb` may close
it; that is a schema change and was not tested.

## What you gain, concretely

These are all runtime failures in `engine-store` today, and become compile errors:

| Mistake | Compile error |
|---|---|
| Nonexistent column | `E0425: cannot find value` |
| Wrong Rust type (`String` for a `Uuid` column) | `E0277` trait bound |
| `filter` on another table's column | `E0271: AppearsInFromClause` |

## What you give up

- **~20-25% throughput vs sqlx**, reproducible across read, write, and both pool sizes. Accepted in
  D84 Amendment 3: the worst configuration tested still sustained >8,000 req/s, against an engine
  that dispatches workflows rather than serving a read-heavy API.
- Slightly worse tail latency (max 43.4ms vs 20.1ms at concurrency 256).

## What was measured as safe

Do not re-litigate these; they were the open risks and they are closed.

- **No deadlock or starvation under pooled concurrency.** 0 failures and 0 panics in every run,
  including `POOL_SIZE=2` at concurrency 256 — 128x oversubscribed. `deadpool` queues gracefully.
- **No connection leak.** `pg_stat_activity` flat at 22 backends across 5 sustained rounds.
- **sqlx and diesel-async coexist in one binary.** No feature-unification or driver conflict, and a
  route touching both stacks per request agreed on 5,120/5,120 requests. **So a staged, file-by-file
  port is safe** — you do not need a big-bang swap.

## Before this reaches the Mini

D84 Amendment 1 records three hardcoded connection strings. Trap 3 fails at *runtime*, per request,
so a bad URL here starts cleanly and then fails every query:

- `scripts/launchd/com.brandon.engine-serve.plist:12`
- `scripts/launchd/com.brandon.bastion-serve.plist:12`
- `bastion/src/config.rs:374`

Also unresolved from D84 Amendment 1 and not this port's to fix, but it will block verification:
**nothing on the Mini applies migrations** — `routine.sh` has no migration step.

## Verifying the port

1. `cargo nextest run -p engine-store` while iterating; `--workspace` once at the end (standing
   rule 8).
2. **New tests that assert a migration applies need a live Postgres.** engine-rs CI currently runs
   **no** Postgres service — every DB test self-skips on unset `DATABASE_URL`. Adding a `postgres:`
   service to CI is required regardless of ORM, and is not diesel-specific.
3. Neither `diesel_migrations::embed_migrations!` nor `sqlx::migrate!` needs a database to
   *compile*. The DB requirement is only for tests that *run* migrations.

## Still untested — know the edges of the evidence

- Diesel's typed DSL against a `jsonb` column (would it close the one unchecked query?).
- `node_invocations` — now exists (`EN.14.F`, [`0002_create_node_invocations.sql`](../crates/engine-store/migrations/0002_create_node_invocations.sql), read/write through `engine_store::{insert_node_invocation, list_node_invocations_for_run}`), and gained `payload`/`payload_truncated`/`payload_cap_bytes` columns (`EN.14.G`, [`0003_add_node_invocation_payload.sql`](../crates/engine-store/migrations/0003_add_node_invocation_payload.sql); `payload` is `json`, not `jsonb`, matching the journal table's convention). Both migrations were added via `sqlx`, not diesel — still nothing modelled for this table under this port.
- Performance of DSL-generated SQL vs hand-written strings. All throughput numbers above came from
  raw `sql_query`.
- `AsyncConnectionWrapper` under concurrent load (boot path only).
- TLS / remote Postgres. Everything ran against a local connection.
